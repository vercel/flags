---
title: Nuxt
description: Set up the Flags SDK in Nuxt with one module.
---

`@flags-sdk/nuxt` connects the Flags SDK to the server of Nuxt (Nitro). It gives each flag the current request through `useEvent()`, loads the configuration files of the folder `flags`, lets `createError()` pass through, starts and closes the providers with the server, compiles your flags files, generates the modules of `flags:<source>`, and registers your flags for Flags Explorer. Your code imports only `flags`.

**Requirements:** Nuxt 4 with Nitro 2.

## Setup

### 1. Install the packages

```sh title="Terminal"
npm install flags @flags-sdk/nuxt @vercel/flags-core
```

`@vercel/flags-core` has the provider of [Vercel Flags](/docs/providers/vercel). It needs no OpenFeature package. Use the provider of your flag management system instead, if you have a different one.

### 2. Add the module

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
  // Compiles the flags files, and writes .flags/self.ts
  modules: ['@flags-sdk/nuxt'],
});
```

The module also enables the async context of Nitro, which the SDK needs to find the current request. It writes the types of `flags:<source>` into `flags/generated.d.ts`, and adds the file to the types of Nuxt, so the types work without more configuration.

### 3. Create the flag in Vercel

With `@vercel/flags-core` in your dependencies, the source `self` uses the provider of Vercel Flags by default: `new VercelProvider()`. You do not create a provider for it.

`VercelProvider` uses the OIDC token of your project. Run `vercel link` and `vercel env pull` once, and create a boolean flag `enableSale` in the dashboard of your project, or with `vercel flags create enableSale --kind boolean`. See [Vercel Flags](/docs/providers/vercel).

Then declare the flag in `app.flags`, in the root of your application, next to `package.json`:

```js title="app.flags"
flag enableSale {
  description: "Shows the summer sale"
  defaultValue: false
}
```

The flags file declares the flags of your code, with their keys, types and default values. Vercel Flags still decides each value. The build reads only the file, so it needs no network and no credentials. Turn on `allowArbitraryExtensions` in `tsconfig.json`, and add `*.d.flags.ts` to `.gitignore`. See [Flags files](/docs/flags/flags-files).

The context is optional. It tells the provider who the user is, e.g. for targeting rules. Add `flags/sources/self/context.ts`. The SDK calls it once per request, and the default provider stays:

```ts title="flags/sources/self/context.ts"
import type { FlagsRequest } from 'flags';

// The evaluation context of all flags of this source, once per request
export default function getEvaluationContext(
  request: FlagsRequest | undefined,
) {
  return { user: request?.cookies?.get('user')?.value ?? 'anonymous' };
}
```

Without `context.ts`, the provider gets only the evaluation context of the call side. In the same way, `provider.ts` replaces the default provider. See [The default source `self`](/docs/flags/code-generation#the-default-source-self).

With another provider, create `flags/sources/self/provider.ts`. To try the SDK without an account, export an in-memory provider of `@openfeature/server-sdk`. See [Code generation](/docs/flags/code-generation#the-folder-of-a-source).

### 4. Use the flag in a server route

Flags run only on the server of Nitro. Evaluate them in a server route:

```ts title="server/api/flags.get.ts"
import { enableSale } from 'flags:self';

// No runtime.onInvoke: the binding gets the request from useEvent()
export default defineEventHandler(async () => ({
  sale: await enableSale(),
}));
```

Load the values in a page with `useFetch`. During server-side rendering, Nuxt calls the route directly and forwards the cookies of the request, so the flags see the same user:

```vue title="app/pages/index.vue"
<script setup lang="ts">
const { data } = await useFetch('/api/flags');
</script>

<template>
  <h1>{{ data?.sale ? 'Summer sale!' : 'Welcome' }}</h1>
</template>
```

Do not import `flags`, `flags:self` or a flags file in components or composables that run in the browser. A new flag in `app.flags` becomes a new export of `flags:self`. See [Code generation](/docs/flags/code-generation).

## Inline flags

An [inline flag](/docs/flags/inline-flags) decides its value in your code. Put inline flags into a module that starts with `'use flags'`:

```ts title="lib/flags.ts"
'use flags';

import { defineFlag } from 'flags';

export const betaBanner = defineFlag({
  key: 'betaBanner',
  decide: (request) => request?.cookies?.get('beta')?.value === '1',
  options: [false, true] as const,
  description: 'Shows the beta banner to testers',
});
```

The module registers the flags of each module that starts with `'use flags'`, so Flags Explorer finds them. The generated `flags:self` module has the directive already. Both kinds of flags are called in the same way:

```ts title="server/api/flags.get.ts"
import { enableSale } from 'flags:self';
import { betaBanner } from '../../lib/flags';

export default defineEventHandler(async () => {
  const sale = await enableSale();
  const beta = await betaBanner();
  return { sale, beta };
});
```

Set the cookie `beta=1` to see the beta banner.

## Without flags files

You can also write the source and its flags by hand. Use `defineSource` and `source.bindFlag`. Without flags files, the code generation writes nothing. To turn off the code generation, use `modules: [['@flags-sdk/nuxt', { disableCodeGeneration: true }]]`.

```ts title="flags/self.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';
import { defineSource } from 'flags';

export const self = defineSource({
  provider: new VercelProvider(),
  project: { system: 'vercel-flags' },
  getEvaluationContext: (request) => ({
    user: request?.cookies?.get('user')?.value ?? 'anonymous',
  }),
});
```

```ts title="lib/flags.ts"
'use flags';

import { self } from '../flags/self';

export const enableSale = self.bindFlag('enableSale', {
  defaultValue: false,
  description: 'Shows the summer sale',
});
```

Each flag is declared on its source. This is the same code that the SDK compiles a flags file into. See [Flags of a source](/docs/flags/provider-flags).

## Optional: the configuration files

You do not need configuration files. Your flags name their source, e.g. `self`, and [overrides](/docs/tooling/overrides) work with `FLAGS_SECRET`, or on Vercel, without them.

Add a file to the folder `flags`, next to `flags/sources`, when you want settings for all flags:

- `flags/hooks.ts`: OpenFeature hooks for every flag, as the default export.
- `flags/config.json`: the static settings, e.g. `"selfSource": false`, or `overrides`: which override cookies the SDK accepts.

The Nuxt module loads the files automatically, from the `flags` folder of your project or of `src`. In development, a change applies without a restart.

```ts title="flags/hooks.ts"
import type { Hook } from 'flags';

const hooks: Hook[] = [
  {
    after: (context, details) => {
      console.log(`${context.flagKey} = ${JSON.stringify(details.value)}`);
    },
  },
];

export default hooks;
```

See [Configuration](/docs/flags/configuration) for all options.

## Errors of Nitro

An error of `createError()` reaches Nitro unchanged, also when you throw it from `getEvaluationContext`. The flag does not catch it and does not return its default value:

```ts title="flags/self.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';
import { defineSource } from 'flags';
import { createError } from '#imports';

export const self = defineSource({
  provider: new VercelProvider(),
  project: { system: 'vercel-flags' },
  getEvaluationContext: (request) => {
    if (request?.cookies?.get('blocked')) {
      throw createError({ statusCode: 403, statusMessage: 'Blocked' });
    }
    return { user: request?.cookies?.get('user')?.value ?? 'anonymous' };
  },
});
```

## Lifecycle

The module starts the providers with the Nitro server and closes them when the server shuts down. You do not call `runtime.onInit()` or `runtime.onShutdown()` yourself.

## Flags Explorer and the manifest

- Nuxt builds the app with Vite and the server with Nitro. The module adds the plugin of `@flags-sdk/vite` to both, so `'use flags'` modules register their flags in pages and in server routes.
- `nuxt dev` serves the [flags manifest](/docs/tooling/flags-manifest) at `/.well-known/flags/manifest.json`, with `cache-control: no-store`.
- `nuxt build` writes `flags-manifest.json` into `.output/server`.
- Overrides of Flags Explorer use the `flag-overrides` cookie. See [Overrides](/docs/tooling/overrides).

To show the values of a request in Flags Explorer, write the flag values element yourself; see [Other frameworks](/docs/frameworks/next/flag-values#other-frameworks).

## How it works

- The module sets `nitro.alias` for `flags/framework` (to `@flags-sdk/nuxt/binding`), for `flags/hooks` and `flags/settings` (to the files of the folder `flags` which exist) and, by default, each `flags:<source>`, and adds `flags` and `@flags-sdk/nuxt` to `nitro.externals.inline`, so that Nitro bundles the SDK and the aliases reach it.
- In development, Nitro loads `flags` from `node_modules`, so a Nitro plugin of the module also registers the binding with `registerFramework` of `flags/tooling`.
- The binding gets the request with `useEvent()` and recognizes errors of `createError()` with `isError()`.
- The module uses the hooks `vite:extendConfig`, `nitro:config` and `prepare:types` (for `flags/generated.d.ts`), so it does not depend on `@nuxt/kit`.

The binding follows the [Flags SDK standard](/docs/standard/framework-bindings).
