title: Nuxt
description: Set up the Flags SDK in Nuxt with one module.
---

`@flags-sdk/nuxt` connects the Flags SDK to the server of Nuxt (Nitro). It gives each flag the current request through `useEvent()`, loads `flags/config.ts`, lets `createError()` pass through, starts and closes the providers with the server, registers your flags for Flags Explorer, and uses the fast provider of Vercel Flags in builds on Vercel. Your code imports only `flags`.

**Requirements:** Nuxt 4 with Nitro 2.

## Setup

### 1. Install the packages

```sh title="Terminal"
npm install flags @flags-sdk/nuxt
```

### 2. Add the module

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
  modules: ['@flags-sdk/nuxt'],
});
```

That is the only required step. The module also enables the async context of Nitro, which the SDK needs to find the current request.

### 3. Define your flags

Create `lib/flags.ts`. It is the same file as in the [other frameworks](/docs/frameworks):

```ts title="lib/flags.ts"
'use flags';

import { TypedInMemoryProvider } from '@openfeature/server-sdk';
import { bindFlag, defineFlag, defineSource } from 'flags';

const shop = defineSource({
  provider: new TypedInMemoryProvider({
    'summer-sale': {
      variants: { on: true, off: false },
      defaultVariant: 'off',
      disabled: false,
      // On for alice only
      contextEvaluator: (context) => (context.user === 'alice' ? 'on' : 'off'),
    },
    checkout: {
      variants: { control: 'control', express: 'express' },
      defaultVariant: 'express',
      disabled: false,
    },
  } as const),
  project: { system: 'in-memory' },
  getEvaluationContext: (_context, request) => ({
    user: request?.cookies?.get('user')?.value ?? 'anonymous',
  }),
});

// Flags of the source: the provider decides the value
export const summerSale = bindFlag({
  key: 'summer-sale',
  source: shop,
  defaultValue: false,
  description: 'The summer sale banner',
});

export const checkout = bindFlag({
  key: 'checkout',
  source: shop,
  type: 'string',
  options: ['control', 'express'],
  defaultValue: 'control',
  description: 'The checkout flow',
});

// An inline flag: your code decides the value
export const betaBanner = defineFlag({
  key: 'beta-banner',
  decide: (_context, request) => request?.cookies?.get('beta')?.value === '1',
  options: [false, true] as const,
  description: 'Shows the beta banner to testers',
});
```

To try the example, install `@openfeature/server-sdk`. For a real project, use the provider of your flag management system, for example [Vercel Flags](/docs/providers/vercel).

### 4. Use the flags in a server route

Flags run only on the server of Nitro. Evaluate them in a server route:

```ts title="server/api/flags.get.ts"
import { evaluate } from 'flags';
import { betaBanner, checkout, summerSale } from '../../lib/flags';

// No runtime.onInvoke: the binding gets the request from useEvent()
export default defineEventHandler(async () => {
  const [sale, flow, beta] = await evaluate([summerSale, checkout, betaBanner]);
  return { sale, flow, beta };
});
```

Load the values in a page with `useFetch`. During server-side rendering, Nuxt calls the route directly and forwards the cookies of the request, so the flags see the same user:

```vue title="app/pages/index.vue"
<script setup lang="ts">
const { data } = await useFetch('/api/flags');
</script>

<template>
  <p v-if="data?.beta">You see the beta.</p>
  <h1>{{ data?.sale ? 'Summer sale!' : 'Welcome' }}</h1>
  <p>Checkout: {{ data?.flow }}</p>
</template>
```

Set the cookie `user=alice` to see the sale, and `beta=1` to see the beta banner. Do not import `flags` in components or composables that run in the browser.

## Optional: `flags/config.ts`

You do not need a configuration file. Your flags name their source, and [overrides](/docs/tooling/overrides) work with `FLAGS_SECRET`, or on Vercel, without one.

Add `flags/config.ts`, next to `flags/sources`, when you want settings for all flags: OpenFeature hooks for every flag, the options of overrides, or a default source for flags without a `source`. The Nuxt module loads it automatically, from the `flags` folder of your project or of `src`. In development, a change applies without a restart.

```ts title="flags/config.ts"
import { defineConfig } from 'flags';

export const config = defineConfig({
  hooks: [
    {
      after: (context, details) => {
        console.log(`${context.flagKey} = ${JSON.stringify(details.value)}`);
      },
    },
  ],
});
```

See [Configuration](/docs/flags/configuration) for all options.

## Errors of Nitro

An error of `createError()` reaches Nitro unchanged, also when you throw it from `getEvaluationContext`. The flag does not catch it and does not return its default value:

```ts title="sources.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';
import { defineSource } from 'flags';
import { createError } from '#imports';

export const vercel = defineSource({
  provider: new VercelProvider(),
  project: { system: 'vercel-flags' },
  getEvaluationContext: (_context, request) => {
    if (request?.cookies?.get('blocked')) {
      throw createError({ statusCode: 403, statusMessage: 'Blocked' });
    }
    return { user: request?.cookies?.get('user')?.value ?? 'anonymous' };
  },
});
```

## Lifecycle

The module starts the providers with the Nitro server and closes them when the server shuts down. You do not call `runtime.onInit()` or `runtime.onShutdown()` yourself.

## Flags Explorer and the manifest

- Nuxt builds the app with Vite and the server with Nitro. The module adds the plugin of `@flags-sdk/vite` to both, so `'use flags'` modules register their flags in pages and in server routes.
- `nuxt dev` serves the [flags manifest](/docs/tooling/flags-manifest) at `/.well-known/flags/manifest.json`, with `cache-control: no-store`.
- `nuxt build` writes `flags-manifest.json` into `.output/server`.
- Overrides of Flags Explorer use the `flag-overrides` cookie. See [Overrides](/docs/tooling/overrides).

To show the values of a request in Flags Explorer, write the flag values element yourself; see [Other frameworks](/docs/frameworks/next/flag-values#other-frameworks).

## Deployment

This only concerns flags without a `source`:

- On Vercel, a build sets `VERCEL`. If the project has `@vercel/flags-core`, the module replaces `flags/default-provider` with `@vercel/flags-core/default-provider` in Nitro. Development does not replace it.
- A `defaultSource` in the optional `flags/config.ts` always wins.
- On another platform, or in a test, pass the module of its provider: `modules: [['@flags-sdk/nuxt', { defaultProvider: './provider.ts' }]]`.

## How it works

- The module sets `nitro.alias` for `flags/framework` (to `@flags-sdk/nuxt/binding`) and `flags/config`, and adds `flags` and `@flags-sdk/nuxt` to `nitro.externals.inline`, so that Nitro bundles the SDK and the aliases reach it.
- In development, Nitro loads `flags` from `node_modules`, so a Nitro plugin of the module also registers the binding with `registerFramework` of `flags/tooling`.
- The binding gets the request with `useEvent()` and recognizes errors of `createError()` with `isError()`.
- The module uses the hooks `vite:extendConfig` and `nitro:config`, so it does not depend on `@nuxt/kit`.

The binding follows the [Flags SDK standard](/docs/standard/framework-bindings).
