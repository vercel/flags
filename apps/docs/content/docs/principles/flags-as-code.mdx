---
title: Flags as Code
description: Why the Flags SDK turns each feature flag into a typed function that you declare once and call anywhere.
---

The Flags SDK works differently from the SDKs of most feature flag providers.
It puts a few constraints in place, and these constraints lead to a better
experience when you use flags across a codebase.

## Consistent, predictable call sites

With the SDK of a typical feature flag provider, you call a client with the
key of the flag as a string:

```ts
// A typical feature flag SDK, here the OpenFeature client
const showBanner = await client.getBooleanValue('summer-sale', false, {
  targetingKey: user.id,
});
```

With the Flags SDK, you call the flag itself:

```ts
// The Flags SDK
const showBanner = await summerSale();
```

To get there, you declare the flag once:

```ts title="flags.ts"
'use flags';

import { bindFlag } from 'flags';

export const summerSale = bindFlag({
  key: 'summer-sale',
  defaultValue: false,
  description: 'Shows the summer sale banner',
});
```

`bindFlag` declares a flag whose value comes from a flag management system,
through a [source](/docs/flags/provider-flags). If the code decides the value,
use `defineFlag` with a `decide` function instead. Both return the same kind of
flag, and you call both the same way. See
[the two kinds of flags](/docs/flags).

## Feature flags are functions

Each flag is its own function, so the implementation can change without
touching the call sites. You can move a flag from an inline `decide` function
to a provider, or from one provider to another, and no page needs to change.

Because flags are regular exports, your editor's tools work with them. "Find
all references" shows where a flag is still used, "Rename symbol" renames it,
and deleting the export shows every place that still needs it as a type error.

## Feature flags declare their type and default value

The declaration contains everything the call site needs to know: the `type`
(`boolean`, `string`, `number` or `object`), the known `options`, and the
`defaultValue`.

```ts title="flags.ts"
export const checkout = bindFlag({
  key: 'checkout',
  type: 'string',
  options: ['control', 'express'],
  defaultValue: 'control',
});

// The type of the value is 'control' | 'express' | (string & {})
const flow = await checkout();
```

The default value lives on the declaration, so it is the same for every
evaluation. When the provider fails, the flag returns its `defaultValue` and
logs one line. A flag without a `defaultValue` throws a `FlagEvaluationError`
instead, so you decide per flag whether a failure is acceptable. See
[Errors and default values](/docs/flags/errors-and-default-values).

## Feature flags declare how their context is established

Traditional SDKs ask for the evaluation context on each call:

```ts
// A typical feature flag SDK, here the OpenFeature client
const context = { targetingKey: user.id, plan: user.plan };
const value = await client.getBooleanValue('summer-sale', false, context);
```

Every call site has to build the context again. If one call site builds it
differently, or forgets a field, the same flag can return different values on
the same page.

The Flags SDK moves this work out of the call site. A source creates the
evaluation context once, from the current request, for all of its flags:

```ts title="sources.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';
import { defineSource } from 'flags';

export const vercel = defineSource({
  provider: new VercelProvider(),
  project: { system: 'vercel-flags' },
  getEvaluationContext: (_context, request) => ({
    user: request?.cookies?.get('user')?.value ?? 'anonymous',
  }),
});
```

The call site only passes what it alone knows, for example a team from the
URL, and TypeScript checks that it passes it. The source runs once per request,
and each flag is evaluated once per request, so all parts of a page see the
same value. See [Evaluation Context](/docs/principles/evaluation-context).

## Avoid vendor lock-in

When you use the SDK of one provider directly, it tends to spread through the
codebase over time, and switching providers later means changing every call
site.

The Flags SDK is built on [OpenFeature](https://openfeature.dev). A source
takes any OpenFeature server provider as it is, without a wrapper or an
adapter. To switch providers, change the provider of the source:

```ts title="sources.ts"
import { defineSource } from 'flags';
import { provider } from './provider';

export const shop = defineSource({
  // Any OpenFeature server provider, e.g. of Vercel Flags,
  // LaunchDarkly, GrowthBook or flagd
  provider,
});
```

Your flag declarations and call sites stay the same. See
[Providers](/docs/providers) for the providers you can use.

## Define once, use in any framework

Your application code imports only `flags`. The framework package
(`@flags-sdk/next`, `@flags-sdk/sveltekit`, `@flags-sdk/nuxt`,
`@flags-sdk/tanstack-start`, `@flags-sdk/hono` or `@flags-sdk/express`) gives
the SDK the current request, loads the optional `flags/config.ts`, and lets the signals of
the framework through. The same flag module works in Next.js, in SvelteKit, in
a Hono server, or in a plain Node.js script, because the
[standard](/docs/standard) defines the contract between frameworks and the
SDK.

See [Frameworks](/docs/frameworks) for the setup of each framework.
