Where feature flags are evaluated, and what data they need, determines the
latency you pay to evaluate them.

To evaluate a feature flag, two kinds of data are needed:

- The **definition** contains the rules of the flag, such as who should see a
  feature. It usually comes from a flag management system, through its
  provider.
- The **evaluation context** is data about the user or entity the flag is
  evaluated for, such as a user ID or the plan of a team.

You can think of an evaluation like this:

```
evaluate(definition, evaluation context) = value
```

A flag that is on or off for everyone needs no evaluation context. A flag that
is on only for some users does.

## Where feature flags can be evaluated

- **Server-side** code runs in the
  [function region](https://vercel.com/docs/functions/configuring-functions/region)
  of the project: server components, route handlers, loaders, server actions
  and API servers.
- **Routing Middleware** (the proxy in Next.js) runs before the cache, close to
  the visitor.
- **Client-side** code runs in the browser. The Flags SDK does not evaluate
  flags there. See [Server-side vs Client-side](/docs/principles/server-side-vs-client-side).

Each place has different costs for loading definitions and for establishing
the evaluation context. For example, if Routing Middleware has to make a
network request to find out who the current user is, every request pays for
it.

## How feature flag definitions are loaded

Provider SDKs usually bootstrap the definitions with a network request, and
then keep them up to date, for example with a streaming connection. Evaluation
then happens in memory, without a request per flag.

This model works well for long-running servers, but serverless functions live
much shorter. They pay the cost of the bootstrap more often, and many
instances with their own connections put load on the flag management system.

Two things help:

- **Initialize early.** The runtime initializes the provider of each source
  once and reuses it for all requests of the process. Framework packages call
  `runtime.onInit()` at startup where the framework has a hook for it.
  Without a framework, call it yourself. See
  [Without a framework](/docs/frameworks/node).
- **Use a provider that keeps definitions close.** For example,
  `VercelProvider` of Vercel Flags evaluates in memory, and keeps its
  definitions current by streaming or polling. On Vercel, it can also start
  from definitions included in the deployment. See
  [Vercel Flags](/docs/providers/vercel).

## Evaluating on the server

Evaluating on the server is the most common way to use the Flags SDK, and the
most straightforward one.

The function region is usually close to the database of your application, so
it is acceptable to load data for the evaluation context there, for example a
team from the database. Load it once per request: a source's
`getEvaluationContext` runs once per request and input, also when many flags
use the source. See [Evaluation Context](/docs/principles/evaluation-context).

## Evaluating in Routing Middleware

To evaluate flags in Routing Middleware, you need the definitions and the
evaluation context there.

A provider that evaluates in memory gives you the definitions at low latency.
The evaluation context depends on your application, so it is up to you to
provide it quickly.

Avoid making a network request or reading a database in Routing Middleware to
establish the evaluation context. Instead, store the information the flags
need in a cookie when a user signs in. The browser sends the cookie with each
request, and the source can read it from the request:

```ts title="flags.config.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';
import { defineConfig, defineSource } from 'flags';

export const config = defineConfig({
  defaultSource: defineSource({
    provider: new VercelProvider(),
    project: { system: 'vercel-flags' },
    // Reads the cookie. No database request in the proxy
    getEvaluationContext: (_context, request) => ({
      targetingKey: request?.cookies?.get('user-id')?.value ?? 'anonymous',
    }),
  }),
});
```

Where needed, sign or encrypt the cookie so that visitors can not change it or
read its contents.

In Next.js, [precompute](/docs/frameworks/next/precompute) evaluates a group
of flags in the proxy and rewrites the request to a static variant of the
page.

## Deduplicating work

Wherever flags are evaluated, avoid establishing the same evaluation context
twice. The Flags SDK does this for you:

- Each step of the evaluation context chain runs once per request and input.
- Each flag is evaluated once per request and input, so all parts of a page
  get the same value.

In v4, you wrapped functions in `dedupe` for this. In v5, it is built into the
runtime. See [Evaluating flags](/docs/flags/evaluating-flags).

## Evaluating on the client

The Flags SDK does not evaluate flags in the browser. Evaluate them on the
server, and pass the values to the client, for example as props of a client
component.
