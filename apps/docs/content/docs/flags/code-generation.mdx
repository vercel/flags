The code generation writes two things from your [flags files](/docs/flags/flags-files):

- one module for each source, so that you can import a flag from its source, `flags:<source>`;
- the types of the flags files and of `flags:<source>`.

```ts title="app/page.tsx"
import { checkout, summerSale } from 'flags:self';

const sale = await summerSale();
const flow = await checkout();
```

The code generation reads only your flags files. It uses no network and no credentials, so each build gives the same result, also offline and in CI. A new flag is a new block in a flags file, e.g. `app.flags`, and the next generation adds it to `flags:self`.

The plugins of [Next.js](/docs/frameworks/next), [SvelteKit](/docs/frameworks/sveltekit), [Nuxt](/docs/frameworks/nuxt) and [TanStack Start](/docs/frameworks/tanstack-start) run the code generation and resolve `flags:<source>` for you. Without a bundler, e.g. with [Hono](/docs/frameworks/hono), [Express](/docs/frameworks/express) or [plain Node.js](/docs/frameworks/node), you import the flags from their flags files, and `flags sync` writes the types (see [Without a framework plugin](#without-a-framework-plugin)).

## The modules of `flags:<source>`

`flags:<source>` has the flags of that source from all flags files of your application. The source of a flag is its field `source`, or the source of its file (see [A flag of another source](/docs/flags/flags-files#a-flag-of-another-source)).

```js title="app.flags"
source self

flag summerSale {
  key: "summer-sale"
  defaultValue: false
}
```

```js title="app/checkout/checkout.flags"
source self

flag checkout {
  options: ["control", "express"]
  defaultValue: "control"
}
```

The generator writes `.flags/self.ts`. It re-exports the flags of the source `self` from each file, with their names:

```ts title=".flags/self.ts (generated)"
export { summerSale } from '../app.flags';
export { checkout } from '../app/checkout/checkout.flags';
```

Thus an import from `flags:self` and an import from the file give the same flag, and both work in one application:

```ts
import { summerSale } from 'flags:self';
// The same flag as
import { summerSale } from './app.flags';
```

- **A flags file without flags is valid.** It defines its source. An empty `app.flags` gives `flags:self` with no exports, e.g. before the first flag of a new application.
- **Without a flags file of a source, there is no `flags:<source>`.** The bundler can not resolve an import of it, and the type check fails.
- **A key or a name in two files of one source is a conflict.** The second flag is not in `flags:<source>`. `flags sync` and a build fail, e.g. `flags: The key "checkout" of the source "self" is declared in app.flags and in checkout/checkout.flags. Declare it in one file.` The dev server reports the conflict, and goes on.

## The folder of a source

The source of a flags file is the folder `flags/sources/<source>` of your application, with one file and two optional files:

```text
app.flags           # source self (the default)
app/
  marketing.flags   # source marketing
flags/
  sources/
    self/
      provider.ts   # The OpenFeature provider
      context.ts    # Optional: getEvaluationContext(request, input)
      hooks.ts      # Optional: the OpenFeature hooks of the source
    marketing/
      provider.ts
  generated.d.ts    # Generated: the types of flags:self and flags:marketing
.flags/             # Generated, Git ignores it
  self.ts           # The module of flags:self
  marketing.ts      # The module of flags:marketing
```

The folder `flags` is in the root of your application, or in `src` (`src/flags/sources/<source>`). The SDK looks in the same places as for the files of the [configuration](/docs/flags/configuration), e.g. `flags/hooks.ts`. In SvelteKit, use `src/flags`, since SvelteKit type-checks `src` only.

| File | Default export |
| --- | --- |
| `provider.ts` | The OpenFeature provider |
| `context.ts` (optional) | `getEvaluationContext(request, input)`, as for [`defineSource`](/docs/flags/provider-flags#sources) |
| `hooks.ts` (optional) | The OpenFeature hooks of the source, as `hooks` of `defineSource` |

The files can also be `.mts`, `.tsx`, `.js` or `.mjs`. The name of the folder is the name of the source. It must start with a letter, and contain only letters, digits, `-` and `_`. Each source needs `provider.ts`. The exception is the [default source `self`](#the-default-source-self) of Vercel Flags. Without a provider, the build fails, e.g. `The source "shop" needs flags/sources/shop/provider.ts.`

### `provider.ts`

The default export is the OpenFeature provider of the source, e.g. Vercel Flags:

```ts title="flags/sources/self/provider.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';

export default new VercelProvider();
```

### `context.ts`

This file is optional. The default export creates the evaluation context for the provider. It is the `getEvaluationContext` of the source, and runs once per request:

```ts title="flags/sources/self/context.ts"
import type { FlagsRequest } from 'flags';

export default function getEvaluationContext(
  request: FlagsRequest | undefined,
) {
  return { user: request?.cookies?.get('user')?.value ?? 'anonymous' };
}
```

The second parameter, `input`, is the evaluation context of the call side. Leave it out if you do not need it. If you declare it with a type, e.g. `input: { teamId: string }`, the flags of the source require that context at each call, as with a hand-written source. See [The evaluation context](/docs/flags/evaluation-context).

Without `context.ts`, the source has no `getEvaluationContext`. The provider gets only the evaluation context of the call side, and the flags take no input.

### `hooks.ts`

This file is optional. The default export is an array of OpenFeature hooks. They run for each flag of the source, as the `hooks` of `defineSource`:

```ts title="flags/sources/self/hooks.ts"
import type { Hook } from 'flags';

const hooks: Hook[] = [
  {
    after(hookContext, details) {
      console.log(`${hookContext.flagKey}: ${details.value}`);
    },
  },
];

export default hooks;
```

The hooks of the source run after the hooks of `flags/hooks.ts`, and before the hooks of the call. See [Configuration](/docs/flags/configuration#flagshooksts).

## The default source `self`

An application which depends on `@vercel/flags-core` needs no folder for the source `self`. Its provider is `new VercelProvider()` of `@vercel/flags-core/openfeature`, and its project is your Vercel project, so Flags Explorer links each flag to its page in the dashboard of Vercel Flags. The provider uses the OIDC token of `vercel link` and `vercel env pull`, or the SDK key in the environment variable `FLAGS`.

You still declare each flag in a flags file:

```js title="app.flags"
flag enableSale {
  defaultValue: false
}
```

```ts title="app/page.tsx"
import { enableSale } from 'flags:self';
```

The SDK turns the default provider on when `package.json` has `@vercel/flags-core` in any dependency field, e.g. `dependencies` or `devDependencies`. Each file in `flags/sources/self` replaces its part:

- `context.ts` adds an evaluation context, e.g. for targeting rules. The provider stays the default.
- `provider.ts` replaces the provider, e.g. `new VercelProvider(createClient(...))` with an SDK key of your choice.
- `hooks.ts` adds OpenFeature hooks for the flags of the source.

```text
flags/
  sources/
    self/
      context.ts    # Only the context. The provider is the default.
```

Each other source, and `self` without `@vercel/flags-core`, needs `provider.ts`.

### Turn it off

Set `"selfSource": false` in [`flags/config.json`](/docs/flags/configuration#flagsconfigjson) to turn off the default provider. Then the source `self` needs `flags/sources/self/provider.ts`, as each other source.

```json title="flags/config.json"
{
  "$schema": "https://flags-sdk.dev/schemas/config.v1.json",
  "selfSource": false
}
```

The framework plugins and the commands `flags sync` and `flags watch` read the same file, so the setting applies to all of them.

## Where the types go

The generator writes two kinds of types:

- **A declaration file next to each flags file**, e.g. `app.d.flags.ts` for `app.flags`. It has the type of each flag of the file. Turn on `allowArbitraryExtensions` in `tsconfig.json`, and let Git ignore `*.d.flags.ts`. See [TypeScript](/docs/flags/flags-files#typescript).
- **`flags/generated.d.ts`**. It declares the module `flags:<source>` of each source. The type of each flag is the type of its export in its flags file, with the same JSDoc. TypeScript includes the file with its default `include` (`**/*.ts`), so you do not configure `paths`.

`flags/generated.d.ts` goes into the folder `flags` which exists, in the root of your application or in `src`, e.g. the folder with `flags/sources` or `flags/hooks.ts`. Without one, it goes to `src/flags/generated.d.ts` if your application has a `src` directory, otherwise to `flags/generated.d.ts`, and the SDK creates the folder. If the place changes, the SDK removes the old `generated.d.ts`, so that only one file declares the modules. A `generated.d.ts` which the SDK did not write stays.

The generator writes a file only when its content changes, never writes half a file, and removes the module of a source which no flags file has any more. Without flags files, it writes nothing.

## Set it up

### 1. Add a flags file

Create `app.flags` in the root of your project, next to `package.json`, and declare your flags. See [Flags files](/docs/flags/flags-files). For a source other than the default source `self` of Vercel Flags, also add `flags/sources/<source>/provider.ts`, as above. In SvelteKit, put the flags files and the folder `flags` into `src`.

### 2. Add the plugin

Add the plugin of your framework. The plugin compiles the flags files, and the code generation is on by default:

```ts tab="Next.js" title="next.config.ts"
import { withFlags } from '@flags-sdk/next/plugin';

export default withFlags({});
```

```ts tab="SvelteKit" title="vite.config.ts"
import { flags } from '@flags-sdk/sveltekit/vite';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [sveltekit(), flags()],
});
```

```ts tab="Nuxt" title="nuxt.config.ts"
export default defineNuxtConfig({
  modules: ['@flags-sdk/nuxt'],
});
```

```ts tab="TanStack Start" title="vite.config.ts"
import { flags } from '@flags-sdk/tanstack-start/vite';
import { tanstackStart } from '@tanstack/react-start/plugin/vite';
import viteReact from '@vitejs/plugin-react';
import { nitro } from 'nitro/vite';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [nitro(), tanstackStart(), viteReact(), flags()],
});
```

The plugin writes `.flags/<source>.ts` for each source of your flags files, and the types. It points each `flags:<source>` import to its module:

- A build (`next build`, `vite build`, `nuxt build`) writes the modules one time.
- The dev server (`next dev`, `vite dev`, `nuxt dev`) writes the modules before it resolves the imports, and again after each change of a flags file.
- The production server does no code generation.

Restart the dev server after you add a flags file with a new source, because the alias of the new source is new. The plugin watches the folders of the sources, so a new `context.ts` needs no restart.

To turn off the code generation, use `disableCodeGeneration: true`, e.g. `withFlags({}, { disableCodeGeneration: true })`, `flags({ disableCodeGeneration: true })` or `modules: [['@flags-sdk/nuxt', { disableCodeGeneration: true }]]`. The plugin still compiles the flags files, so imports from the files work. `withFlags` still reads `.flags/aliases.json`, e.g. after `flags sync`.

### 3. Commit or ignore the types

The folder `.flags` has its own `.gitignore`, so Git ignores the generated modules. You do not change your `.gitignore` for them.

The plugin writes `flags/generated.d.ts` and the declaration files again for each dev server and each build, and `flags sync` writes them too. You can commit `flags/generated.d.ts`, so that a type check works before the first build. Or you can ignore it, and run `flags sync` before the type check in CI:

```json title="package.json"
{
  "scripts": {
    "type-check": "flags sync && tsc --noEmit"
  }
}
```

### 4. Import the flags

```ts
import { enableSale } from 'flags:self';

const sale = await enableSale();
```

## Without a framework plugin

Hono, Express and plain Node.js have no bundler, so they have no plugin. Start Node.js with the hooks of the SDK, which compile the flags files, and import your flags from their files:

```sh title="Terminal"
node --import flags/register server.ts
```

```ts title="server.ts"
import { enableSale } from './app.flags';
```

The `flags` command line of the `flags` package writes the modules and the types:

```sh title="Terminal"
# Write once, e.g. before a type check
npx flags sync

# Write, and again after each change of a flags file.
# Starts the command after the first write.
npx flags watch -- node --import flags/register --watch server.ts
```

Both commands take an optional directory, e.g. `flags sync apps/shop`. A typical `package.json`:

```json title="package.json"
{
  "scripts": {
    "dev": "flags watch -- node --import flags/register --watch server.ts",
    "type-check": "flags sync && tsc --noEmit"
  }
}
```

With another Vite setup, the plugin `flags` of `@flags-sdk/vite` runs the code generation in the same way, and resolves `flags:<source>` for you. See [Framework packages](/docs/api-reference/framework-packages).

See [CLI](/docs/tooling/cli) for all options of the commands.

## Flags files and the runtime

The flags files only shape the code. At runtime, the provider decides every value, as with a hand-written flag:

- A flag works before it exists in your flag management system: the provider returns `FLAG_NOT_FOUND`, and the flag returns its `defaultValue`. Without a `defaultValue`, the call throws a `FlagEvaluationError`. See [Errors and default values](/docs/flags/errors-and-default-values).
- A variant that is added after the deployment works at once: options do not limit the value.
- When you remove a flag from a flags file, it disappears from `flags:<source>` at the next generation, so TypeScript shows each place that still uses it.
