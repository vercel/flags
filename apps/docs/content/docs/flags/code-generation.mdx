---
title: Code generation
description: Put the provider, the context and the catalog of a source in flags/sources, and import each flag from flags:<source>.
---

Code generation is the file system API of the Flags SDK. You describe a source with three files in `flags/sources/<source>`, and the SDK writes the `defineSource` and `bindFlag` calls for you, from the catalog of your flag management system. Then you import each flag by its key:

```ts title="app/page.tsx"
import { evaluate } from 'flags';
import { checkout, 'summer-sale' as summerSale } from 'flags:self';

const [sale, flow] = await evaluate([summerSale, checkout]);
```

A new flag in your flag management system becomes a new export of `flags:self`, with its type, its variants, its description and its default value. You do not write a declaration for it.

The plugins of [Next.js](/docs/frameworks/next), [SvelteKit](/docs/frameworks/sveltekit), [Nuxt](/docs/frameworks/nuxt) and [TanStack Start](/docs/frameworks/tanstack-start) generate the modules and resolve `flags:<source>` for you. This is the recommended way for these frameworks. Without a bundler, e.g. with [Hono](/docs/frameworks/hono), [Express](/docs/frameworks/express) or [plain Node.js](/docs/frameworks/node), you write the sources by hand (see [Provider flags](/docs/flags/provider-flags)), or generate the modules with `flags sync` and import them by their path.

## Generated code is hand-written code

The generator writes plain SDK code, the same that you can write yourself. Nothing in the runtime knows whether a flag was generated. These two modules give the same flags:

```ts title="flags.ts (by hand)"
'use flags';

import { bindFlag, defineSource } from 'flags';
import provider from './flags/sources/self/provider.ts';
import getEvaluationContext from './flags/sources/self/context.ts';

const source = defineSource({
  provider,
  project: { system: 'vercel-flags', projectId: 'prj_shop' },
  getEvaluationContext,
});

/** The checkout flow */
export const checkout = bindFlag({
  key: 'checkout',
  source,
  type: 'string',
  options: ['control', 'express'],
  description: 'The checkout flow',
  defaultValue: 'control',
});

/** The summer sale banner */
export const summerSale = bindFlag({
  key: 'summer-sale',
  source,
  type: 'boolean',
  options: [false, true],
  description: 'The summer sale banner',
  defaultValue: false,
});
```

```ts title=".flags/self.ts (generated)"
// Generated by flags sync / flags watch. Do not edit.
'use flags';

import { bindFlag, defineSource } from 'flags';
import getEvaluationContext from '../flags/sources/self/context.ts';
import provider from '../flags/sources/self/provider.ts';

const source = defineSource({
  provider,
  project: {"system":"vercel-flags","projectId":"prj_shop"},
  getEvaluationContext,
});

/**
 * The checkout flow
 */
const flag_0 = bindFlag({
  key: "checkout",
  source,
  type: "string",
  options: ["control","express"] as const,
  description: "The checkout flow",
  defaultValue: "control",
});
export { flag_0 as "checkout" };

/**
 * The summer sale banner
 */
const flag_1 = bindFlag({
  key: "summer-sale",
  source,
  type: "boolean",
  options: [false,true] as const,
  description: "The summer sale banner",
  defaultValue: false,
});
export { flag_1 as "summer-sale" };
```

Thus, you can start with code generation and switch to hand-written flags later, or the other way around, without changing the code that calls the flags. Overrides, hooks, the evaluation context, one value per request and Flags Explorer work the same for both.

The only difference is the export name: the generated module exports each flag under its key, so a key can contain any character. Import a key that is not a valid name with a string import, e.g. `import { 'summer-sale' as summerSale } from 'flags:self'`.

## The folder of a source

Each source is a folder `flags/sources/<source>` in your application, with three files. By convention, the main source of an application is `self`:

```text
flags/
  sources/
    self/
      catalog.ts    # The flags of the source, for the generator only
      provider.ts   # The OpenFeature provider
      context.ts    # getEvaluationContext(request, input)
    marketing/      # Optional: a second source, e.g. a second system
      catalog.ts
      provider.ts
      context.ts
.flags/             # Generated, add it to .gitignore
  self.ts           # The module of flags:self
  marketing.ts      # The module of flags:marketing
```

| File | Default export | Runs |
| --- | --- | --- |
| `catalog.ts` | A `CatalogLoader`: returns one catalog, or yields a catalog after each change | In Node.js, only when the code is generated |
| `provider.ts` | The OpenFeature provider | In your application |
| `context.ts` | `getEvaluationContext(request, input)`, as for [`defineSource`](/docs/flags/provider-flags#sources) | In your application |

The name of the folder is the name of the source, and the module is `flags:<source>`. It must start with a letter, and contain only letters, digits, `-` and `_`. Each folder needs all three files.

### `provider.ts`

The default export is the OpenFeature provider of the source, e.g. Vercel Flags:

```ts title="flags/sources/self/provider.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';

export default new VercelProvider();
```

### `context.ts`

The default export creates the evaluation context for the provider. It is the `getEvaluationContext` of the source, and runs once per request:

```ts title="flags/sources/self/context.ts"
import type { FlagsRequest } from 'flags';

export default function getEvaluationContext(
  request: FlagsRequest | undefined,
) {
  return { user: request?.cookies?.get('user')?.value ?? 'anonymous' };
}
```

The second parameter, `input`, is the evaluation context of the call side. Leave it out if you do not need it. If you declare it with a type, e.g. `input: { teamId: string }`, the flags of the source require that context at each call, as with a hand-written source. See [The evaluation context](/docs/flags/evaluation-context).

### `catalog.ts`

The default export loads the catalog: the flags of the source at one point in time. The generator uses it to write `.flags/<source>.ts`. Your application never imports it, so it can use the credentials of an admin API, and these credentials do not reach the generated code.

```ts
interface Catalog {
  flags: {
    [key: string]: {
      variants: unknown[];
      description?: string;
      defaultValue?: unknown; // the value when the evaluation fails
    };
  };
  project?: Project; // as for defineSource, e.g. { system: 'vercel-flags', projectId }
  revision?: number; // changes with each change of the catalog, if the system has one
}
```

A **static catalog** returns one catalog, e.g. from a list in your code or from one request to the API of your system. A list in your code is a good start:

```ts title="flags/sources/self/catalog.ts"
import type { CatalogLoader } from 'flags';

const loadCatalog: CatalogLoader = () => ({
  flags: {
    enableSale: {
      variants: [false, true],
      description: 'Shows the summer sale',
      defaultValue: false,
    },
  },
});

export default loadCatalog;
```

`defaultValue` is optional. The generator writes it as the `defaultValue` of the flag: the value that the flag returns when its evaluation fails, e.g. the fallback variant of your system.

A **streaming catalog** is an async generator. It yields a complete catalog first, and again after each change. In development, the generator then rewrites the module, so a new flag in your dashboard appears in your editor without a restart. `signal` aborts when the generator stops, e.g. after a build or at the end of the dev server:

```ts title="flags/sources/self/catalog.ts"
import { setTimeout as sleep } from 'node:timers/promises';
import type { Catalog, CatalogLoadOptions } from 'flags';

interface RemoteFlag {
  key: string;
  variants: unknown[];
  description?: string;
  fallback?: unknown;
}

async function fetchCatalog(signal: AbortSignal): Promise<Catalog> {
  // The admin API of your flag management system
  const response = await fetch('https://flags.example.com/api/flags', {
    headers: { authorization: `Bearer ${process.env.FLAGS_API_TOKEN}` },
    signal,
  });
  if (!response.ok) {
    throw new Error(`Could not load the flags (${response.status}).`);
  }
  const body = (await response.json()) as { flags: RemoteFlag[] };
  return {
    flags: Object.fromEntries(
      body.flags.map((flag) => [
        flag.key,
        {
          variants: flag.variants,
          description: flag.description,
          defaultValue: flag.fallback,
        },
      ]),
    ),
  };
}

export default async function* loadCatalog({
  signal,
}: CatalogLoadOptions): AsyncGenerator<Catalog> {
  while (!signal.aborted) {
    yield await fetchCatalog(signal);
    // Check again in 10 seconds. A system with a stream API can yield on each change instead.
    await sleep(10_000, undefined, { signal }).catch(() => {});
  }
}
```

The [playground app](https://github.com/vercel/flags/tree/main/apps/playground) of the repository has a streaming catalog of Vercel Flags, which subscribes to the changes of a project.

<Callout type="info">
  Node.js loads `catalog.ts` with its built-in type stripping, without a bundler. Use a Node.js version that strips types by default (22.18 or newer), use only erasable TypeScript syntax (no `enum`), and import other files of the source with their `.ts` extension, e.g. `import { selfFlags } from './definitions.ts'`.
</Callout>

## What the generator writes

For each source, `.flags/<source>.ts` contains:

- the `'use flags'` directive, so the framework packages register the flags and Flags Explorer finds them;
- one `defineSource` with `provider.ts`, `context.ts` and the `project` of the catalog, if it has one;
- one `bindFlag` for each flag of the catalog, sorted by key, with:
  - `type` from the variants: `boolean`, `string` or `number` if all variants have that type, otherwise `object` (any JSON value, e.g. for variants of mixed types);
  - `options`: the variants. As for every flag, they do not limit the value: a variant that is added after the deployment goes through;
  - `description`, also as JSDoc, so your editor shows it;
  - `defaultValue`, if the catalog has one for the flag.

The generator writes a file only when its content changes, never writes half a file, and removes the module of a removed source. If a catalog fails, the last generated modules stay.

<Callout type="warning">
  A generated flag without a `defaultValue` in the catalog throws a `FlagEvaluationError` when its evaluation fails. Give each flag a `defaultValue` in `catalog.ts` where a safe value exists, e.g. the fallback variant of your flag management system. See [Errors and default values](/docs/flags/errors-and-default-values).
</Callout>

## Set it up

### 1. Add the folder of the source

Create `flags/sources/self` in the root of your project, next to `package.json`, with `provider.ts`, `context.ts` and `catalog.ts`, as above.

### 2. Turn on code generation

Turn on `codeGeneration` in the plugin of your framework:

```ts tab="Next.js" title="next.config.ts"
import { withFlags } from '@flags-sdk/next/plugin';

export default withFlags({}, { codeGeneration: true });
```

```ts tab="SvelteKit" title="vite.config.ts"
import { flags } from '@flags-sdk/sveltekit/vite';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [sveltekit(), flags({ codeGeneration: true })],
});
```

```ts tab="Nuxt" title="nuxt.config.ts"
export default defineNuxtConfig({
  modules: [['@flags-sdk/nuxt', { codeGeneration: true }]],
});
```

```ts tab="TanStack Start" title="vite.config.ts"
import { flags } from '@flags-sdk/tanstack-start/vite';
import { tanstackStart } from '@tanstack/react-start/plugin/vite';
import viteReact from '@vitejs/plugin-react';
import { nitro } from 'nitro/vite';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [
    nitro(),
    tanstackStart(),
    viteReact(),
    flags({ codeGeneration: true }),
  ],
});
```

The plugin writes `.flags/<source>.ts` for each folder of `flags/sources`, and points each `flags:<source>` import to its module:

- The dev server (`next dev`, `vite dev`, `nuxt dev`) generates the modules before it resolves the imports, and keeps the catalogs open: a change of a catalog rewrites the module.
- A build generates the modules once, then closes the catalogs.
- The production server does no catalog work.

Restart the dev server after you change a file of a source, or add or remove a source.

### 3. Configure TypeScript

The generated modules import `provider.ts` and `context.ts` with their `.ts` extension. Point `flags:*` to the generated modules for the types, and allow these imports:

```json tab="Next.js" title="tsconfig.json"
{
  "compilerOptions": {
    "allowImportingTsExtensions": true,
    "noEmit": true,
    "paths": {
      "flags:*": ["./.flags/*"]
    }
  },
  "include": ["**/*.ts", "**/*.tsx", ".flags/**/*.ts"]
}
```

```js tab="SvelteKit" title="svelte.config.js"
import adapter from '@sveltejs/adapter-node';

/** @type {import('@sveltejs/kit').Config} */
export default {
  kit: {
    adapter: adapter(),
    // The types of flags:self
    alias: { 'flags:self': '.flags/self.ts' },
  },
};
```

```jsonc tab="Nuxt" title="tsconfig.json"
{
  // The module adds flags:<source> to the aliases of Nuxt,
  // so the generated tsconfig of Nuxt has the paths
  "extends": "./.nuxt/tsconfig.json"
}
```

```json tab="TanStack Start" title="tsconfig.json"
{
  "compilerOptions": {
    "allowImportingTsExtensions": true,
    "noEmit": true,
    "paths": {
      "flags:*": ["./.flags/*"]
    }
  }
}
```

In SvelteKit, also set `"allowImportingTsExtensions": true` in the `compilerOptions` of `tsconfig.json`, and add `".flags"` to its `include` (see the [SvelteKit example](https://github.com/vercel/flags/tree/main/examples/standard/sveltekit-codegen)). `allowImportingTsExtensions` needs `noEmit` (or `emitDeclarationOnly`), which most framework setups use already.

### 4. Ignore the generated folder

```text title=".gitignore"
.flags
```

The modules are generated again for each build, from the current catalog.

### 5. Import the flags

```ts
import { enableSale } from 'flags:self';

const sale = await enableSale();
```

## Without a framework plugin

For other setups, generate the modules with the `flags` command line of the `flags` package:

```sh title="Terminal"
# Generate once, e.g. before a build or a type check
npx flags sync

# Generate, and again after each change of a catalog.
# Starts the command after the first generation.
npx flags watch -- node --watch server.ts
```

Both commands take an optional directory, `flags sync [dir]`, and load the `.env` files of that directory first, for the credentials of your catalogs (`.env.<mode>.local`, `.env.local`, `.env.<mode>`, `.env`). The mode is `production` with `--production` or `NODE_ENV=production`, otherwise `development`.

Without a bundler, e.g. with Hono, Express or plain Node.js, import the generated module by its path:

```ts title="server.ts"
import { enableSale } from './.flags/self.ts';
```

A typical `package.json`:

```json title="package.json"
{
  "scripts": {
    "dev": "flags watch -- node --watch server.ts",
    "build": "flags sync && tsc --noEmit"
  }
}
```

With another Vite setup, the plugin `flags` of `@flags-sdk/vite` has the same `codeGeneration` option, and resolves `flags:<source>` for you. See [Framework packages](/docs/api-reference/framework-packages).

See [CLI](/docs/tooling/cli) for all options of the commands.

## Catalogs and the runtime

The catalog only shapes the code. At runtime, the provider decides every value, as with a hand-written flag:

- A flag that is added to your system after the deployment has no export yet. It appears with the next generation, e.g. the next build.
- A variant that is added after the deployment works at once: options do not limit the value.
- A flag that is removed from your system disappears from the module at the next generation, so TypeScript shows each place that still uses it.
