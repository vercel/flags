---
title: Code generation
description: Put the provider, the context and the catalog of a source in flags/sources, and import each flag from flags:<source>.
---

Code generation is the file system API of the Flags SDK. You describe a source with two files, and an optional `context.ts`, in `flags/sources/<source>`, and the SDK writes the `defineSource` and `bindFlag` calls for you, from the catalog of your flag management system. Then you import each flag by its key:

```ts title="app/page.tsx"
import { evaluate } from 'flags';
import { checkout, 'summer-sale' as summerSale } from 'flags:self';

const [sale, flow] = await evaluate([summerSale, checkout]);
```

A new flag in your flag management system becomes a new export of `flags:self`, with its type, its variants, its description and its default value. You do not write a declaration for it.

The plugins of [Next.js](/docs/frameworks/next), [SvelteKit](/docs/frameworks/sveltekit), [Nuxt](/docs/frameworks/nuxt) and [TanStack Start](/docs/frameworks/tanstack-start) generate the modules and resolve `flags:<source>` for you. This is the recommended way for these frameworks. Without a bundler, e.g. with [Hono](/docs/frameworks/hono), [Express](/docs/frameworks/express) or [plain Node.js](/docs/frameworks/node), you write the sources by hand (see [Provider flags](/docs/flags/provider-flags)), or generate the modules with `flags sync` and import them by their path.

## Generated code is hand-written code

The generator writes plain SDK code, the same that you can write yourself. Nothing in the runtime knows whether a flag was generated. These two modules give the same flags:

```ts title="flags.ts (by hand)"
'use flags';

import { bindFlag, defineSource } from 'flags';
import provider from './flags/sources/self/provider.ts';
import getEvaluationContext from './flags/sources/self/context.ts';

const source = defineSource({
  provider,
  project: { system: 'vercel-flags', projectId: 'prj_shop' },
  getEvaluationContext,
});

/** The checkout flow */
export const checkout = bindFlag({
  key: 'checkout',
  source,
  type: 'string',
  options: ['control', 'express'],
  description: 'The checkout flow',
  defaultValue: 'control',
});

/** The summer sale banner */
export const summerSale = bindFlag({
  key: 'summer-sale',
  source,
  type: 'boolean',
  options: [false, true],
  description: 'The summer sale banner',
  defaultValue: false,
});
```

```ts title=".flags/self.ts (generated)"
// Generated by flags sync / flags watch. Do not edit.
'use flags';

import { bindFlag, defineSource } from 'flags';
import getEvaluationContext from '../flags/sources/self/context.ts';
import provider from '../flags/sources/self/provider.ts';

const source = defineSource({
  provider,
  project: {"system":"vercel-flags","projectId":"prj_shop"},
  getEvaluationContext,
});

/**
 * The checkout flow
 */
const flag_0 = bindFlag({
  key: "checkout",
  source,
  type: "string",
  options: ["control","express"] as const,
  description: "The checkout flow",
  defaultValue: "control",
});
export { flag_0 as "checkout" };

/**
 * The summer sale banner
 */
const flag_1 = bindFlag({
  key: "summer-sale",
  source,
  type: "boolean",
  options: [false,true] as const,
  description: "The summer sale banner",
  defaultValue: false,
});
export { flag_1 as "summer-sale" };
```

Thus, you can start with code generation and switch to hand-written flags later, or the other way around, without changing the code that calls the flags. Overrides, hooks, the evaluation context, one value per request and Flags Explorer work the same for both.

The only difference is the export name: the generated module exports each flag under its key, so a key can contain any character. Import a key that is not a valid name with a string import, e.g. `import { 'summer-sale' as summerSale } from 'flags:self'`.

## The folder of a source

Each source is a folder `flags/sources/<source>` in your application, with two files and two optional files. By convention, the main source of an application is `self`:

```text
flags/
  sources/
    self/
      catalog.ts    # The flags of the source, for the generator only
      provider.ts   # The OpenFeature provider
      context.ts    # Optional: getEvaluationContext(request, input)
      hooks.ts      # Optional: the OpenFeature hooks of the source
    marketing/      # Optional: a second source, e.g. a second system
      catalog.ts
      provider.ts
  generated.d.ts    # Generated: the types of flags:self and flags:marketing
.flags/             # Generated, Git ignores it
  self.ts           # The module of flags:self
  marketing.ts      # The module of flags:marketing
```

The folder `flags` is in the root of your application, or in `src` (`src/flags/sources/<source>`). The SDK looks in the same places as for the files of the [configuration](/docs/flags/configuration), e.g. `flags/hooks.ts`. In SvelteKit, use `src/flags`, since SvelteKit type-checks `src` only.

| File | Default export | Runs |
| --- | --- | --- |
| `catalog.ts` | A `CatalogLoader`: returns one catalog, or yields a catalog after each change | In Node.js, only when the code is generated |
| `provider.ts` | The OpenFeature provider | In your application |
| `context.ts` (optional) | `getEvaluationContext(request, input)`, as for [`defineSource`](/docs/flags/provider-flags#sources) | In your application |
| `hooks.ts` (optional) | The OpenFeature hooks of the source, as `hooks` of `defineSource` | In your application |

The name of the folder is the name of the source, and the module is `flags:<source>`. It must start with a letter, and contain only letters, digits, `-` and `_`. Each folder needs `provider.ts` and `catalog.ts`. `context.ts` and `hooks.ts` are optional. The exception is the [default source `self`](#the-default-source-self) of Vercel Flags.

### `provider.ts`

The default export is the OpenFeature provider of the source, e.g. Vercel Flags:

```ts title="flags/sources/self/provider.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';

export default new VercelProvider();
```

### `context.ts`

This file is optional. The default export creates the evaluation context for the provider. It is the `getEvaluationContext` of the source, and runs once per request:

```ts title="flags/sources/self/context.ts"
import type { FlagsRequest } from 'flags';

export default function getEvaluationContext(
  request: FlagsRequest | undefined,
) {
  return { user: request?.cookies?.get('user')?.value ?? 'anonymous' };
}
```

The second parameter, `input`, is the evaluation context of the call side. Leave it out if you do not need it. If you declare it with a type, e.g. `input: { teamId: string }`, the flags of the source require that context at each call, as with a hand-written source. See [The evaluation context](/docs/flags/evaluation-context).

Without `context.ts`, the source has no `getEvaluationContext`. The provider gets only the evaluation context of the call side, and the generated flags take no input. Restart the dev server after you add or remove `context.ts`.

### `hooks.ts`

This file is optional. The default export is an array of OpenFeature hooks. They run for each flag of the source, as the `hooks` of `defineSource`:

```ts title="flags/sources/self/hooks.ts"
import type { Hook } from 'flags';

const hooks: Hook[] = [
  {
    after(hookContext, details) {
      console.log(`${hookContext.flagKey}: ${details.value}`);
    },
  },
];

export default hooks;
```

The hooks of the source run after the hooks of `flags/hooks.ts`, and before the hooks of the call. See [Configuration](/docs/flags/configuration#flagshooksts). Restart the dev server after you add or remove `hooks.ts`.

### `catalog.ts`

The default export loads the catalog: the flags of the source at one point in time. The generator uses it to write `.flags/<source>.ts`. Your application never imports it, so it can use the credentials of an admin API, and these credentials do not reach the generated code.

```ts
interface Catalog {
  flags: {
    [key: string]: {
      variants: unknown[];
      description?: string;
      defaultValue?: unknown; // the value when the evaluation fails
    };
  };
  project?: Project; // as for defineSource, e.g. { system: 'vercel-flags', projectId }
  revision?: number; // changes with each change of the catalog, if the system has one
}
```

For Vercel Flags, `@vercel/flags-core/catalog` is a complete catalog loader. It reads the flags of your Vercel project, and yields a new catalog after each change in Vercel:

```ts title="flags/sources/self/catalog.ts"
export { default } from '@vercel/flags-core/catalog';
```

It gives no `defaultValue`. See [Vercel Flags](/docs/providers/vercel#the-catalog) for its options. For other systems, write the catalog loader yourself, as below.

A **static catalog** returns one catalog, e.g. from a list in your code or from one request to the API of your system. A list in your code is a good start:

```ts title="flags/sources/self/catalog.ts"
import type { CatalogLoader } from 'flags';

const loadCatalog: CatalogLoader = () => ({
  flags: {
    enableSale: {
      variants: [false, true],
      description: 'Shows the summer sale',
      defaultValue: false,
    },
  },
});

export default loadCatalog;
```

`defaultValue` is optional. The generator writes it as the `defaultValue` of the flag: the value that the flag returns when its evaluation fails, e.g. the fallback variant of your system.

A **streaming catalog** is an async generator. It yields a complete catalog first, and again after each change. In development, the generator then rewrites the module, so a new flag in your dashboard appears in your editor without a restart. `signal` aborts when the generator stops, e.g. after a build or at the end of the dev server:

```ts title="flags/sources/self/catalog.ts"
import { setTimeout as sleep } from 'node:timers/promises';
import type { Catalog, CatalogLoadOptions } from 'flags';

interface RemoteFlag {
  key: string;
  variants: unknown[];
  description?: string;
  fallback?: unknown;
}

async function fetchCatalog(signal: AbortSignal): Promise<Catalog> {
  // The admin API of your flag management system
  const response = await fetch('https://flags.example.com/api/flags', {
    headers: { authorization: `Bearer ${process.env.FLAGS_API_TOKEN}` },
    signal,
  });
  if (!response.ok) {
    throw new Error(`Could not load the flags (${response.status}).`);
  }
  const body = (await response.json()) as { flags: RemoteFlag[] };
  return {
    flags: Object.fromEntries(
      body.flags.map((flag) => [
        flag.key,
        {
          variants: flag.variants,
          description: flag.description,
          defaultValue: flag.fallback,
        },
      ]),
    ),
  };
}

export default async function* loadCatalog({
  signal,
}: CatalogLoadOptions): AsyncGenerator<Catalog> {
  while (!signal.aborted) {
    yield await fetchCatalog(signal);
    // Check again in 10 seconds. A system with a stream API can yield on each change instead.
    await sleep(10_000, undefined, { signal }).catch(() => {});
  }
}
```

<Callout type="info">
  Node.js loads `catalog.ts` with its built-in type stripping, without a bundler. Use a Node.js version that strips types by default (22.18 or newer), use only erasable TypeScript syntax (no `enum`), and use relative imports for the other files of the source, e.g. `import { selfFlags } from './definitions'`. You do not need the `.ts` extension: the SDK finds the `.ts`, `.tsx` or `/index.ts` file of an import.
</Callout>

## The default source `self`

An application which depends on `@vercel/flags-core` has the source `self` by default. It has the flags of your Vercel project, and you do not create `flags/sources/self`:

```ts title="app/page.tsx"
import { enableSale } from 'flags:self';
```

The SDK turns it on when `package.json` has `@vercel/flags-core` in any dependency field, e.g. `dependencies` or `devDependencies`. An application without `@vercel/flags-core` never gets the default source: the SDK does no network request and writes no file for it.

The default source has these parts:

| Part | Default |
| --- | --- |
| Provider | `new VercelProvider()` of `@vercel/flags-core/openfeature`. It uses the OIDC token of `vercel link` and `vercel env pull`, or the SDK key in the environment variable `FLAGS`. |
| Catalog | `@vercel/flags-core/catalog`, from the dependencies of your application. A build takes the first catalog. The dev server stays connected, and rewrites the module after each change in Vercel. |
| Context | None. The provider gets only the evaluation context of the call side. |

The catalog gives the `project` of the source, so each flag links to its page in the dashboard of Vercel Flags.

### Replace a part

Each file in `flags/sources/self` replaces its part of the default source. The other parts stay the defaults:

- `context.ts` adds an evaluation context, e.g. for targeting rules. The provider and the catalog stay the defaults.
- `provider.ts` replaces the provider, e.g. `new VercelProvider(createClient(...))` with an SDK key of your choice.
- `catalog.ts` replaces the catalog, e.g. with a static catalog that has a `defaultValue` for each flag.
- `hooks.ts` adds OpenFeature hooks for the flags of the source.

```text
flags/
  sources/
    self/
      context.ts    # Only the context. The provider and the catalog are the defaults.
```

Restart the dev server after you add or remove a file. Each other source, and `self` without `@vercel/flags-core`, needs `provider.ts` and `catalog.ts`, as above.

### Where the types go

If your application has a folder `flags/sources`, the types go to `flags/generated.d.ts` next to it, as for each source. Without it, the types go into a folder `flags` which exists, e.g. with `flags/hooks.ts` or `flags/config.json`. Without one, they go to `src/flags/generated.d.ts` if your application has a `src` directory, otherwise to `flags/generated.d.ts`, and the SDK creates the folder. If the place changes, e.g. when you add `flags/sources/self/` in the root, the SDK removes the old `generated.d.ts`, so that only one file declares `flags:self`. The module is `.flags/self.ts`, as for each source.

### Without credentials

The default catalog needs the credentials of Vercel Flags. If it can not load the flags before its first catalog, e.g. in CI without `vercel env pull`, `flags:self` has no flags and the SDK warns:

```txt
flags: The default source "self" has no flags, because the flags of Vercel Flags could not be loaded: … Run `vercel link` and `vercel env pull`, or set `"selfSource": false` in flags/config.json.
```

The build does not fail. A type check then fails at each import of a flag of `flags:self`. A `catalog.ts` of your own still fails the build when it fails.

### Turn it off

Set `"selfSource": false` in [`flags/config.json`](/docs/flags/configuration#flagsconfigjson) to turn off the default source. This also stops the network requests of the code generation to Vercel Flags. Set it if you depend on `@vercel/flags-core` but write your sources by hand.

```json title="flags/config.json"
{
  "$schema": "https://flags-sdk.dev/schemas/config.v1.json",
  "selfSource": false
}
```

The framework plugins and the commands `flags sync` and `flags watch` read the same file, so the setting applies to all of them.

## What the generator writes

For each source, `.flags/<source>.ts` contains:

- the `'use flags'` directive, so the framework packages register the flags and Flags Explorer finds them;
- one `defineSource` with `provider.ts` (or `new VercelProvider()` for the default source `self`), `context.ts` and `hooks.ts` (if the folder has them) and the `project` of the catalog, if it has one;
- one `bindFlag` for each flag of the catalog, sorted by key, with:
  - `type` from the variants: `boolean`, `string` or `number` if all variants have that type, otherwise `object` (any JSON value, e.g. for variants of mixed types);
  - `options`: the variants. As for every flag, they do not limit the value: a variant that is added after the deployment goes through;
  - `description`, if the catalog has one;
  - `defaultValue`, if the catalog has one for the flag;
  - a JSDoc comment with what the catalog knows about the flag, so your editor shows it: the description, the variants and the default value. A long variant is shortened, and the JSDoc shows at most 10 variants.

The generator also writes `flags/generated.d.ts`, next to `flags/sources`. It declares the module `flags:<source>` of each source, with the type of each flag. TypeScript includes the file with its default `include` (`**/*.ts`), so you do not configure TypeScript. Each source has a named type, e.g. `SelfSource`, so your editor shows a short type for a flag, e.g. `Flag<SelfSource, "enableSale", undefined, boolean>`.

The generator writes a file only when its content changes, never writes half a file, and removes the module of a removed source. If a catalog fails, the last generated modules stay.

<Callout type="warning">
  A generated flag without a `defaultValue` in the catalog throws a `FlagEvaluationError` when its evaluation fails. Give each flag a `defaultValue` in `catalog.ts` where a safe value exists, e.g. the fallback variant of your flag management system. See [Errors and default values](/docs/flags/errors-and-default-values).
</Callout>

## Set it up

### 1. Add the folder of the source

Create `flags/sources/self` in the root of your project, next to `package.json`, with `provider.ts`, `catalog.ts` and, if you need it, `context.ts`, as above. In SvelteKit, create `src/flags/sources/self`. With `@vercel/flags-core`, skip this step, or add only the files that you want to replace (see [The default source `self`](#the-default-source-self)).

### 2. Add the plugin

Add the plugin of your framework. Code generation is on by default:

```ts tab="Next.js" title="next.config.ts"
import { withFlags } from '@flags-sdk/next/plugin';

export default withFlags({});
```

```ts tab="SvelteKit" title="vite.config.ts"
import { flags } from '@flags-sdk/sveltekit/vite';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [sveltekit(), flags()],
});
```

```ts tab="Nuxt" title="nuxt.config.ts"
export default defineNuxtConfig({
  modules: ['@flags-sdk/nuxt'],
});
```

```ts tab="TanStack Start" title="vite.config.ts"
import { flags } from '@flags-sdk/tanstack-start/vite';
import { tanstackStart } from '@tanstack/react-start/plugin/vite';
import viteReact from '@vitejs/plugin-react';
import { nitro } from 'nitro/vite';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [nitro(), tanstackStart(), viteReact(), flags()],
});
```

The plugin writes `.flags/<source>.ts` for each folder of `flags/sources` and for the default source `self`, and `flags/generated.d.ts` for the types. It points each `flags:<source>` import to its module:

- The dev server (`next dev`, `vite dev`, `nuxt dev`) generates the modules before it resolves the imports, and keeps the catalogs open: a change of a catalog rewrites the module.
- A build generates the modules once, then closes the catalogs.
- The production server does no catalog work.

Restart the dev server after you change a file of a source, or add or remove a source.

Without a folder `flags/sources` and without the default source `self`, the plugin writes nothing. To turn off code generation, e.g. if you write your sources by hand, use `disableCodeGeneration: true`, e.g. `withFlags({}, { disableCodeGeneration: true })`, `flags({ disableCodeGeneration: true })` or `modules: [['@flags-sdk/nuxt', { disableCodeGeneration: true }]]`.

### 3. Commit or ignore the types

The folder `.flags` has its own `.gitignore`, so Git ignores the generated modules. You do not change your `.gitignore`.

The plugin writes `flags/generated.d.ts` again for each dev server, each build and each `flags sync`. You can commit it, so that a type check works before the first build. Or you can ignore it, and run `flags sync` before the type check in CI:

```json title="package.json"
{
  "scripts": {
    "type-check": "flags sync && tsc --noEmit"
  }
}
```

### 4. Import the flags

```ts
import { enableSale } from 'flags:self';

const sale = await enableSale();
```

## Without a framework plugin

For other setups, generate the modules with the `flags` command line of the `flags` package:

```sh title="Terminal"
# Generate once, e.g. before a build or a type check
npx flags sync

# Generate, and again after each change of a catalog.
# Starts the command after the first generation.
npx flags watch -- node --watch server.ts
```

Both commands take an optional directory, `flags sync [dir]`, and load the `.env` files of that directory first, for the credentials of your catalogs (`.env.<mode>.local`, `.env.local`, `.env.<mode>`, `.env`). The mode is `production` with `--production` or `NODE_ENV=production`, otherwise `development`.

Without a bundler, e.g. with Hono, Express or plain Node.js, import the generated module by its path:

```ts title="server.ts"
import { enableSale } from './.flags/self.ts';
```

A typical `package.json`:

```json title="package.json"
{
  "scripts": {
    "dev": "flags watch -- node --watch server.ts",
    "build": "flags sync && tsc --noEmit"
  }
}
```

With another Vite setup, the plugin `flags` of `@flags-sdk/vite` generates the code in the same way, and resolves `flags:<source>` for you. See [Framework packages](/docs/api-reference/framework-packages).

See [CLI](/docs/tooling/cli) for all options of the commands.

## Catalogs and the runtime

The catalog only shapes the code. At runtime, the provider decides every value, as with a hand-written flag:

- A flag that is added to your system after the deployment has no export yet. It appears with the next generation, e.g. the next build.
- A variant that is added after the deployment works at once: options do not limit the value.
- A flag that is removed from your system disappears from the module at the next generation, so TypeScript shows each place that still uses it.
