The Flags SDK is built on [OpenFeature](https://openfeature.dev/), the open standard for feature flags. It uses OpenFeature server providers as they are: no adapter, no wrapper and no OpenFeature client. The SDK does the work of the OpenFeature client itself, and adds what web servers need: one evaluation context per request, typed flags, overrides and discovery.

## Any server provider plugs in directly

Pass the provider to `defineSource`, the same object that you would give to `OpenFeature.setProvider`:

```sh title="Terminal"
npm install flags @openfeature/server-sdk @openfeature/flagd-provider
```

```ts title="flags.ts"
import { FlagdProvider } from '@openfeature/flagd-provider';
import { bindFlag, defineSource } from 'flags';

const flagd = defineSource({
  provider: new FlagdProvider(),
  getEvaluationContext: (_context, request) => ({
    targetingKey: request?.cookies?.get('user')?.value ?? 'anonymous',
  }),
});

export const newCheckout = bindFlag({
  key: 'new-checkout',
  source: flagd,
  defaultValue: false,
});
```

The provider of Vercel Flags is an OpenFeature provider too, `VercelProvider` of `@vercel/flags-core/openfeature`. See [Providers](/docs/providers) for the providers of other systems, and [Custom providers](/docs/providers/custom-providers) to write your own.

The SDK has no dependency on `@openfeature/*`. It declares its own types (`Provider`, `EvaluationContext`, `Hook`, ...), and its tests check that the types of `@openfeature/server-sdk` fit them. A provider usually needs `@openfeature/server-sdk` as its own peer dependency.

## What the SDK does for each provider

Without an OpenFeature client, the SDK takes over the client's part of the contract:

| OpenFeature | In the Flags SDK |
| --- | --- |
| `OpenFeature.setProvider(provider)` | `defineSource({ provider })` |
| `provider.initialize()` | Called once before the first evaluation, or by `runtime.onInit()`. Shared by all sources of the provider. Retried after a failure. |
| `provider.onClose()` | Called by `runtime.onShutdown()`. The next use initializes the provider again. |
| `client.getBooleanValue(key, default, context)` | `await flag()`. The `type` of the flag selects `resolveBooleanEvaluation`, `resolveStringEvaluation`, `resolveNumberEvaluation` or `resolveObjectEvaluation`. |
| API, client and invocation hooks | Hooks of `flags.config.ts`, of the source and of the call |
| Provider hooks (`provider.hooks`) | Run as in OpenFeature |
| `OpenFeature.addHandler(event, handler)` | `runtime.addHandler(event, handler)` |
| `client.track(name, context, details)` | `track(name, options)` or `track(source, name, options)` |
| Evaluation context | Created per request by the [evaluation context chain](/docs/flags/evaluation-context) |

## Hooks

A hook is an OpenFeature `Hook` with the stages `before`, `after`, `error` and `finally`. Hooks written for the OpenFeature server SDK work as they are.

Hooks come from four places, and run in the order of OpenFeature:

| OpenFeature | Flags SDK | Where |
| --- | --- | --- |
| API | `hooks` of the configuration | `defineConfig({ hooks })` in `flags.config.ts` |
| Client | `hooks` of the source | `defineSource({ hooks })` |
| Invocation | `hooks` of the call | `flag({ hooks, hookHints })`, `evaluate(flags, { hooks })` |
| Provider | `provider.hooks` | the provider |

```ts title="flags.config.ts"
import { defineConfig, type Hook } from 'flags';

const timing: Hook = {
  before(hookContext) {
    hookContext.hookData.set('start', Date.now());
  },
  finally(hookContext, details) {
    const start = hookContext.hookData.get('start') as number;
    console.log(`${hookContext.flagKey}=${details.value} (${details.reason}) in ${Date.now() - start} ms`);
  },
};

export const config = defineConfig({ hooks: [timing] });
```

- `before` runs from the first hook to the last. `after`, `error` and `finally` run from the last hook to the first.
- `before` can return a context. The SDK merges it into a new object, and the next hooks and the provider receive it. The context of the request does not change.
- Each hook has its own `hookData` during one evaluation.
- An error in `before` or `after` fails the evaluation: `error` and `finally` run, then the flag returns its `defaultValue` or throws. An error in `error` or `finally` is logged.
- Hooks run once the evaluation context exists. An error before that, e.g. in `getEvaluationContext`, runs no hooks.
- During one request, a flag is evaluated once, so the hooks run once. A result from the cache of the request runs no hooks. A call with its own `hooks` gets its own evaluation.
- In `hookContext`, `clientMetadata` has `sdk: 'js-server'`, `paradigm: 'server'` and the metadata of the provider. There is no domain.

### Hooks also run for overrides

An override from Flags Explorer does not call the provider, but all hooks run, also the hooks of the provider. The evaluation details have the reason `OVERRIDE`. Thus, a hook can leave overrides out of the exposures of an experiment, or report them:

```ts title="flags.config.ts"
import { defineConfig, OVERRIDE_REASON } from 'flags';

export const config = defineConfig({
  hooks: [
    {
      after(hookContext, details) {
        if (details.reason === OVERRIDE_REASON) {
          reportOverride(hookContext.flagKey, details.value);
        }
      },
    },
  ],
});
```

A hook that does not check the reason counts an override as a usual evaluation.

## Reasons

The reason in the evaluation details tells why a flag has its value. The reasons of the provider pass through unchanged, e.g. `STATIC`, `TARGETING_MATCH`, `SPLIT`, `DEFAULT`, `DISABLED` or `CACHED`. The SDK adds:

| Reason | Constant | Meaning |
| --- | --- | --- |
| `OVERRIDE` | `OVERRIDE_REASON` | An override cookie set the value. The provider was not called. |
| `DECIDE` | `DECIDE_REASON` | The `decide` function of an [inline flag](/docs/flags/inline-flags) set the value. |
| `ERROR` | | The evaluation failed. `errorCode` and `errorMessage` tell why. The value is the `defaultValue`, or a placeholder. |

The error codes are those of OpenFeature, e.g. `FLAG_NOT_FOUND`, `TYPE_MISMATCH` or `PROVIDER_FATAL`. A failed evaluation throws a `FlagEvaluationError` with the same `code`, unless the flag has a `defaultValue` (see [Errors and default values](/docs/flags/errors-and-default-values)).

## Events

The runtime listens to the events of each provider (`provider.events`), from its first initialization until the shutdown:

```ts title="startup.ts"
import { runtime } from 'flags';

runtime.addHandler('PROVIDER_CONFIGURATION_CHANGED', (details) => {
  console.log(`${details.providerName} changed: ${details.flagsChanged}`);
});
```

- The events are `PROVIDER_READY`, `PROVIDER_ERROR`, `PROVIDER_CONFIGURATION_CHANGED` and `PROVIDER_STALE`.
- The runtime emits `PROVIDER_READY` when `initialize` resolves, and `PROVIDER_ERROR` when it rejects, as the OpenFeature SDK does.
- A handler for the current status of a provider runs at once, e.g. `PROVIDER_READY` for a provider that is ready.
- A handler receives the events of all providers, with `providerName`. Handlers for one source are not supported: filter by `providerName`.
- `runtime.removeHandler(event, handler)` removes a handler. Errors of handlers are logged.
- Only `PROVIDER_FATAL` changes evaluations: a provider that reports it fails each evaluation with `PROVIDER_FATAL` until `runtime.onShutdown()`. `ERROR` and `STALE` do not stop evaluations, as in OpenFeature.

## Tracking

`track` gives a tracking event to the provider, e.g. a purchase for an experiment:

```ts title="app/checkout/actions.ts"
import { track } from 'flags';
import { shop } from './sources';

// The provider of the default source
await track('purchase', { details: { value: 99 } });

// The provider of a specific source, with an evaluation context
await track(shop, 'purchase', {
  evaluationContext: { userId: 'alice' },
  details: { value: 99 },
});
```

- The provider receives the evaluation context of the source, as for a flag: `evaluationContext` goes to the `getEvaluationContext` of the source. During a request, the source also reads the request, once per request.
- `track` waits for the initialization of the provider. OpenFeature does not call `track` on a provider that is not ready.
- A provider without `track` ignores the event.
- Errors are logged, not thrown.

## What is the same, and what differs

If you know the OpenFeature server SDK, most things work as you expect.

**The same:**

- The provider interface, unchanged: any OpenFeature server provider works.
- One initialization per provider, `onClose` at the shutdown, and a new initialization after a shutdown.
- Hooks: the four places, the order, the stages, `hookData` and `hookHints`.
- Event names and statuses, and handlers that run at once for the current status.
- The shape of the evaluation context, the evaluation details, the reasons and the error codes.
- `track` and its details.

**Different:**

- **No client and no global API.** You do not call `OpenFeature.setProvider` or `OpenFeature.getClient`. Each source holds its provider, and the SDK calls it directly. There are no domains.
- **The context is per request.** Instead of a global context or a transaction context, the [evaluation context chain](/docs/flags/evaluation-context) creates the context from the request and the call side, once per request.
- **Flags are declared in code.** Each flag has a key, a type, options and a default value in one place, and TypeScript checks its value and its context. You call `await flag()`, not `client.getBooleanValue(key, false, context)`.
- **One value per request.** A flag is evaluated once per request and context, so a page stays consistent.
- **The SDK waits for the provider.** The OpenFeature client returns the default with `PROVIDER_NOT_READY` while a provider initializes. The Flags SDK waits for the initialization, like `setProviderAndWait`, so a cold start does not return default values.
- **Errors throw without a default value.** The OpenFeature client always returns the default value. A flag of the Flags SDK returns its `defaultValue` if it has one, and otherwise throws a `FlagEvaluationError`.
- **The value, not the details.** A flag returns its value. To read the reason or the variant, use a hook.
- **Overrides.** Flags Explorer can override any flag for your browser, with the reason `OVERRIDE` (see [Overrides](/docs/tooling/overrides)).
- **`initialize` gets no context.** The SDK calls `initialize()` without a context, because server providers evaluate with a context per request. `onContextChanged` is not used.

<Callout type="warning">
  Do not register a provider instance with the OpenFeature API and also give it to a source. It would be initialized and closed twice. If you use the OpenFeature client elsewhere in the same application, create a separate provider instance for the Flags SDK.
</Callout>
