A flag of a source gets its value from a flag management system, e.g. Vercel Flags. Each flag of a source has two parts:

- a **source** with `defineSource`: the OpenFeature provider of the system, the project in that system, and how to create the evaluation context;
- one **flag** for each key with `source.bindFlag`.

There are two ways to get these calls:

- **[Flags files](/docs/flags/flags-files)**. You declare the flags in `app.flags`, and put the provider and the evaluation context of the source in the folder `flags/sources/self`. The SDK compiles the flags file into the `defineSource` and `source.bindFlag` calls for you. You import the flags from `./app.flags`, or with `import { summerSale } from 'flags:self'` (see [Code generation](/docs/flags/code-generation)).
- **By hand**, when you prefer to write the code. This page shows that code. It is the same code that the SDK compiles a flags file into.

By convention, the main source of an application is called `self`:

```ts title="flags/self.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';
import { defineSource } from 'flags';

export const self = defineSource({
  provider: new VercelProvider(),
  project: { system: 'vercel-flags' },
  getEvaluationContext: (request) => ({
    user: request?.cookies?.get('user')?.value ?? 'anonymous',
  }),
});
```

```ts title="flags.ts"
'use flags';

import { self } from './flags/self';

export const summerSale = self.bindFlag('summerSale', {
  defaultValue: false,
  description: 'The summer sale banner',
});

export const checkout = self.bindFlag('checkout', {
  type: 'string',
  options: ['control', 'express'],
  defaultValue: 'control',
});
```

```ts title="app/page.tsx"
import { checkout, summerSale } from '../flags';

const sale = await summerSale();
const flow = await checkout();
```

`'use flags'` at the top of `flags.ts` is optional. It marks a module that exports only flags, so that Flags Explorer can find them (see [Flags manifest](/docs/tooling/flags-manifest)). That is why the source has its own module.

<Callout type="info">
  With a flags file, you do not write this module. `app.flags` declares the flags, the folder `flags/sources/self` has a `provider.ts` and an optional `context.ts`, and the SDK compiles `app.flags` into the same `defineSource` and `source.bindFlag` calls. See [Flags files](/docs/flags/flags-files).
</Callout>

## Sources

```ts
defineSource({ provider, project?, getEvaluationContext?, hooks? });
```

| Option | Meaning |
| --- | --- |
| `provider` | Any OpenFeature server provider, as it is. No adapter or wrapper. See [Providers](/docs/providers). |
| `project` | Optional. The project in the flag management system, e.g. for the links of Flags Explorer to your dashboard. |
| `getEvaluationContext(request, input)` | Optional. Creates the evaluation context for the provider, e.g. from the cookies of the request. See [The evaluation context](/docs/flags/evaluation-context). |
| `hooks` | Optional. OpenFeature hooks for all flags of this source. See [OpenFeature](/docs/flags/openfeature#hooks). |

A source does not change the provider. Several sources can share one provider: the SDK initializes it once.

### The provider

The provider is the OpenFeature server provider of your flag management system, e.g. `VercelProvider` of `@vercel/flags-core/openfeature`. For a demo or a test, the in-memory provider of OpenFeature works too:

```ts title="flags/self.ts"
import { TypedInMemoryProvider } from '@openfeature/server-sdk';
import { defineSource } from 'flags';

export const self = defineSource({
  provider: new TypedInMemoryProvider({
    summerSale: {
      variants: { on: true, off: false },
      defaultVariant: 'off',
      disabled: false,
      // On for alice only
      contextEvaluator: (context) => (context.user === 'alice' ? 'on' : 'off'),
    },
  } as const),
  project: { system: 'in-memory' },
  getEvaluationContext: (request) => ({
    user: request?.cookies?.get('user')?.value ?? 'anonymous',
  }),
});
```

See [OpenFeature providers](/docs/providers/openfeature) for the providers of other systems, and [Custom providers](/docs/providers/custom-providers) to write your own.

### The project

`project` names the project of the flags in the flag management system. Tools use it, e.g. Flags Explorer for a link from each flag to your dashboard. It does not change how flags are evaluated, and you can leave it out.

| `system` | Fields |
| --- | --- |
| `'vercel-flags'` | `projectId?`, `teamId?`. Without them, the project is the Vercel project of the deployment. |
| `'launchdarkly'` | `projectId` (the project key), `teamId?`, `environment?` (needed for the link to a flag) |
| `'in-memory'` | none |

TypeScript checks the fields of each system:

```ts
// Type error: launchdarkly needs projectId
defineSource({ provider, project: { system: 'launchdarkly' } });
```

A system that is not in the list can add itself with a pull request to the SDK. Until then, leave out `project`: the flags work the same, only without links to the dashboard.

## Flags

```ts
source.bindFlag(key, { type?, options?, defaultValue?, description?, getEvaluationContext? });
```

| Option | Meaning |
| --- | --- |
| `key` | Required. The first argument: the key of the flag in the flag management system, e.g. `'summerSale'`. |
| `type` | `'boolean'` (the default), `'string'`, `'number'` or `'object'`. See [Types and options](/docs/flags/types-and-options). |
| `options` | The known values, for Flags Explorer and precompute. They do not limit the value. |
| `defaultValue` | Returned when the evaluation fails. Without it, the call throws. See [Errors and default values](/docs/flags/errors-and-default-values). |
| `description` | What the flag is for, e.g. for Flags Explorer. |
| `getEvaluationContext(request, input)` | Optional. Converts the context of the call side into the context that the source needs. See [The evaluation context](/docs/flags/evaluation-context#the-step-of-the-flag). |

The returned function has the fields of its definition, so tools and your code can read them:

```ts
summerSale.key; // 'summerSale'
summerSale.type; // 'boolean'
summerSale.source.project; // { system: 'vercel-flags' }
checkout.options; // [{ value: 'control' }, { value: 'express' }]
```

## More than one flag management system

Each flag names its own source, so one application can use several systems, or several projects of one system. With flags files, each source is a folder of `flags/sources`, e.g. `flags/sources/blog`, its flags are in a flags file with `source blog`, and you import them from that file or from `flags:blog`. By hand:

```ts title="flags.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';
import { defineSource } from 'flags';

// The flags of a different Vercel project, e.g. of a different team
const blog = defineSource({
  provider: new VercelProvider(process.env.BLOG_FLAGS!),
  project: {
    system: 'vercel-flags',
    projectId: 'prj_blog',
    teamId: 'team_acme',
  },
});

// The flags of the Vercel project of this deployment
const self = defineSource({
  provider: new VercelProvider(),
  project: { system: 'vercel-flags' },
});

export const newSearch = blog.bindFlag('newSearch');
export const summerSale = self.bindFlag('summerSale');
```

With `projectId` and `teamId`, the SDK key of the provider must belong to the same project.

## The provider lifecycle

You do not start or stop providers yourself:

- Defining a flag makes its source known to the SDK. Flags are usually defined at module scope, so the SDK knows all sources before the first request.
- The SDK initializes each provider before its first evaluation. Concurrent evaluations share one initialization, and a failed initialization is retried on the next evaluation.
- A slow provider does not delay the flags of other providers: each flag waits only for the provider of its own source.
- `runtime.onShutdown()` closes the providers, e.g. on `SIGTERM` of a long-running server. See your [framework](/docs/frameworks) for whether it does this for you.

If a source has no flag yet when the process starts, e.g. because its flags are defined in a module that is imported later, register it so that the SDK initializes it early:

```ts title="startup.ts"
import { registerSources } from 'flags/runtime';
import { reports } from './reports-source';

registerSources([reports]);
```

To initialize providers before the first request, e.g. in the init phase of a serverless function without a framework, call `await runtime.onInit()`. See [No framework](/docs/frameworks/node).
