A **provider** connects the Flags SDK to a flag management system, such as Vercel Flags, LaunchDarkly, or your own service. The Flags SDK does not have its own provider format: a provider is an [OpenFeature](https://openfeature.dev/) server provider, used as it is.

This means:

- **No wrappers.** Install the OpenFeature provider of your system and pass it to the SDK. There is no `@flags-sdk/<vendor>` adapter to wait for.
- **No OpenFeature client.** The SDK calls the provider directly. You do not call `OpenFeature.setProvider()` or `OpenFeature.getClient()`.
- **The OpenFeature features you know.** Hooks, provider events, tracking, and evaluation reasons work as in OpenFeature. See [OpenFeature compatibility](/docs/flags/openfeature).

## From a provider to a source

Flags do not use a provider directly. They use a **source**: a provider, plus the function which creates the evaluation context for it, plus an optional description of the flag project for tools. Each flag is declared on its source.

### With flags files

With [flags files](/docs/flags/flags-files), a source is a folder. By convention, the main source of an app is `self`, in `flags/sources/self/`. The provider is the default export of `provider.ts`:

```ts title="flags/sources/self/provider.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';

// Any OpenFeature server provider
export default new VercelProvider();
```

Next to it, the optional `context.ts` creates the evaluation context. You declare the flags of the source in a flags file, e.g. `app.flags`, and import them from the file or from `flags:self` (see [Code generation](/docs/flags/code-generation)). For [Vercel Flags](/docs/providers/vercel), `provider.ts` is optional: with `@vercel/flags-core` in your dependencies, the source `self` uses `new VercelProvider()` by default:

```ts
import { summerSale } from 'flags:self';
```

### By hand

Without a bundler, e.g. with Hono, Express or plain Node.js, or if you prefer to write the code, define the source with `defineSource`:

```ts title="flags/self.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';
import { defineSource } from 'flags';

export const self = defineSource({
  // Any OpenFeature server provider
  provider: new VercelProvider(),
  // Optional: the flag project, for links in Flags Explorer
  project: { system: 'vercel-flags' },
  // Optional: creates the evaluation context, once per request
  getEvaluationContext: (request) => ({
    user: { id: request?.cookies?.get('user-id')?.value ?? 'anonymous' },
  }),
});
```

Declare each flag on its source, with `source.bindFlag(key)`:

```ts title="flags.ts"
'use flags';

import { self } from './flags/self';

export const summerSale = self.bindFlag('summerSale', {
  defaultValue: false,
});
```

A compiled flags file is the same code as this hand-written code. See [Provider flags](/docs/flags/provider-flags) for all options of `defineSource` and `source.bindFlag`.

## The parts of a source

| Option | Required | What it does |
| --- | --- | --- |
| `provider` | Yes | The OpenFeature server provider which evaluates the flags. |
| `getEvaluationContext(request, input)` | No | Creates the evaluation context for the provider from the current request (`headers`, `cookies`, `url`) and the input of the flag. It runs once per request and input. Without it, the provider gets the input as it is. |
| `project` | No | Names the flag project in the flag management system, e.g. `{ system: 'vercel-flags' }`. Flags Explorer uses it for links to the dashboard. Without it, the flags work the same. |
| `hooks` | No | OpenFeature hooks for all flags of this source. |

### Projects and dashboard links

The `project` tells tools where the flags live, so that Flags Explorer can link each flag to its page in the dashboard. The SDK knows these systems today:

| `system` | Fields |
| --- | --- |
| `vercel-flags` | `projectId?`, `teamId?`. Without them, the project of the Vercel deployment. |
| `launchdarkly` | `projectId`, `teamId?`, `environment?`. The link to a flag needs `environment`. |
| `in-memory` | None. For in-memory providers in development and tests. |

A source of a system which is not in this list has no `project`. Its flags evaluate the same way; tools only show no dashboard links. A system adds itself with a pull request, see [The flags manifest format](/docs/standard/flags-manifest-format#system-manifests).

## One provider, many sources

A source is cheap. Several sources can share one provider instance, e.g. to give different flags a different evaluation context. The SDK initializes the provider once, and closes it once.

```ts title="sources.ts"
import { VercelProvider } from '@vercel/flags-core/openfeature';
import { defineSource } from 'flags';

const provider = new VercelProvider();

// Flags about the visitor
export const visitor = defineSource({
  provider,
  project: { system: 'vercel-flags' },
  getEvaluationContext: (request) => ({
    user: { id: request?.cookies?.get('user-id')?.value ?? 'anonymous' },
  }),
});

// Flags about a team: the call side gives the team
export const team = defineSource({
  provider,
  project: { system: 'vercel-flags' },
  getEvaluationContext: (_request, input: { teamId: string }) => ({
    team: { id: input.teamId },
  }),
});
```

TypeScript checks that each flag of `team` gets a `teamId` when you call it: `await teamInsights({ evaluationContext: { teamId } })`. See [Evaluation context](/docs/flags/evaluation-context).

An application can also use more than one flag management system at the same time: each flag is declared on the source it belongs to.

## The lifecycle of a provider

The SDK owns the lifecycle of each provider:

- **Initialization.** The SDK calls `initialize()` once, at `runtime.onInit()` or at the first evaluation which needs the provider. Evaluations wait for it, so a cold start does not return default values. (The OpenFeature client would return the default value with `PROVIDER_NOT_READY` instead.)
- **Evaluation.** The SDK calls `resolveBooleanEvaluation`, `resolveStringEvaluation`, `resolveNumberEvaluation` or `resolveObjectEvaluation`, depending on the `type` of the flag.
- **Shutdown.** The SDK calls `onClose()` at `runtime.onShutdown()`. A later evaluation initializes the provider again.

<Callout>
Do not also register a provider instance that you pass to the SDK with the OpenFeature API, e.g. with `OpenFeature.setProvider()`. Otherwise, the provider is initialized and closed twice.
</Callout>

Importing a module with a source must not open network connections, because tools import your `'use flags'` modules to read the flags (see [The flags manifest](/docs/tooling/flags-manifest)). Most OpenFeature providers connect in `initialize()`, not in their constructor, so this is usually not a concern.
