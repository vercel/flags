Add a header-driven `vercel` client mode that uses timestamps from the `x-vercel-flags-config-versions` request header instead of streaming or polling. Configure `staleWhileRevalidate` (default 60 seconds) and `staleIfError` (default `Infinity`) when creating the client. These options apply to header-driven refreshes, regular polling, and stream reconnection. A healthy stream remains fresh; after disconnection its stale window begins. Successful polls confirm freshness even for unchanged versions. Expired reads share a blocking poll or reconnection wait, bounded to ten seconds, and use the additional error window on failure. Evaluation, bulk evaluation, and `getDatafile()` enforce the same policy. By default, refresh and initialization failures fall back indefinitely to any available data, including unconfirmed bundled/provided data. Explicit finite staleIfError values still enforce expiry. Without available data, or after finite expiry, evaluation uses a supplied default or throws.

Measure freshness from the cached configuration's last accepted fetch or matching-header observation, never its configuration timestamp. Refresh in the background within `staleWhileRevalidate`, otherwise block; after refresh failure, `staleIfError` extends the stale-serving window. Setting either option to `0` disables its corresponding window. Expose optional `fetchedAt` (Unix milliseconds) on datafiles, preserve it through public reads and client creation, and record fetch completion time in generated bundles. Bundled and provided definitions retain that original freshness without requiring confirmation in the current process; only data without a fetch or confirmation timestamp has unknown freshness. Polling and streaming measure freshness from the later of persisted fetch time and runtime confirmation. Older matching headers cannot renew freshness after a newer version has been observed.

Vercel initialization performs no I/O. Headerless reads serve cached data, fetching only when empty, and disabling both streaming and polling preserves offline mode. Share concurrent refreshes while honoring each read's version requirement, catch up to newer observed versions, bound retries with backoff and a deadline, and discard late responses after shutdown.
